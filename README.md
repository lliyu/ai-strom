# ai-storm

让多个模型分角色讨论同一个问题，每个模型用自己的 Lark 群自定义机器人发言，最后由主席把结果写成一份[主文档](#主文档)。

- **decision（方案讨论）**：第 1 轮主笔各自独立出方案 → 之后每轮评审先提意见，主笔看到别人的匿名方案和评审意见后互评并修订，直到所有评审都表示没有新意见（最多 20 轮）→ 主席写主文档：问题、方案、没采用的做法、分歧与待拍板的问题、风险。有新插话的那一轮不会提前结束，主笔要先回应。
- **brainstorm（脑洞风暴）**：给长篇网文想开书的点子，题目可以是一句话脑洞或几个关键词。第 1 轮每位主笔按各自视角发散 3 个 → **暂停，由你挑出要继续讨论的脑洞**，没选的直接放弃 → 每个循环先「盲审」（只给意见、不改写），再各自独立修订 → 主编挑选和组合，写成主文档。不让模型自由群聊，避免几轮之后点子越来越像。
  - 挑选：主编发一张卡片列出所有脑洞的编号和一句话钩子。网页底部勾选（或点「全部保留」），群里回复编号（例如「A1 B3」，大小写、空格都行）或「全部」。认不出编号会提示你重发，讨论一直停着等。没选的不补新的；脑洞全没被选的主笔退出后面的轮次。第 1 轮的脑洞里一个「一句话钩子」都认不出来（格式不对或 mock 演练）时跳过挑选。没有插话通道时（命令行没开插话）也不挑，照常讨论。
  - 之后每轮盲审给每个脑洞先标「【留】B1」或「【弃】B1：理由」。评审过半标【弃】的立即拿掉（有评审时只算评审的票，没有评审时算其他主笔的票），不补新的；主笔的脑洞全被放弃就退出后面的轮次，所有脑洞都被放弃时提前结束。每轮放弃了哪些，主编发一张卡片。
  - 意见分「问题」「可以更大胆的方向」「后续注意」：前两项只写脑洞级的（钩子不抓人、老套路、看不出主角要干什么或爽在哪里、撑不起长篇）；数字、逻辑小漏洞、怎么写某一卷都写进「后续注意」，主笔这轮不用改，主编把它们写进推荐脑洞的「写梗概和大纲时要注意」。评审只因脑洞级问题写「继续讨论」，主笔修订时不许靠新增规则补漏洞。
- **refine（作品打磨）**：在本地网页上从墨稿（novel-idea）挑一份脑洞、梗概、总纲或一段章节细纲，几个模型找不足、讨论怎么改，最后主编写主文档（修改说明）和修订版，你确认后才写回墨稿。不经过 Lark，见[本地网页](#本地网页)。

## 工作方式

```
本机主持程序（node src/cli.js）
  保存完整讨论记录，决定每一轮谁发言、能看到什么
      │                                   │
      ▼ 调用模型                           ▼ 每个发言者用自己的机器人发卡片
  claude CLI / OpenAI 兼容接口         Lark 讨论群（展示过程）
      ▲                                   │
      └──── 每轮开始前用 lark-cli 只读群里的新消息（你的插话）◄┘
```

- 模型之间不在群里直接对话。每一轮由主持程序把别人上一轮的发言（匿名成「方案 A / B / C」）交给每个模型。
- 主席和互评时只看到匿名代号；讨论结束后由程序补发「代号对照」。
- 每次讨论的发言、主文档、追问、用量、插话和工具调用都存进本机的记录库 `local/ai-storm.db`（SQLite），在[本地网页](#本地网页)上看、搜索、归档和删除，见[讨论记录](#讨论记录)。
- 篇幅控制（方案讨论和作品打磨；脑洞风暴不限）：
  - 每条发言开头是不超过 3 行的**要点**。卡片和网页上只露出要点，详细内容放在折叠面板里。飞书客户端要 V7.9 及以上才能显示折叠面板。
  - 主笔从第 2 轮起只写这一轮的变化：改了什么、对评审的回应、立场变化。完整方案写在「【完整方案】」这一行之后，交给评审、其他主笔和主席，卡片上收在「当前完整方案」面板里。
  - 评审只写问题，不写优点，每个问题标【阻断】或【建议】。只有还剩【阻断】级问题才算「继续讨论」；写了继续却没有【阻断】的，按没有意见处理。
  - 每类发言都有字数上限，按去掉空白和 Markdown 符号后的字数计算。超出上限 1.25 倍时，程序会让发言者压缩重写一次，群里只发重写后的版本。上限见配置里的 `limits`。

## 第一次使用

需要 Node.js 20 以上、已登录的 Claude Code CLI（`claude`）。没有第三方依赖，不需要 `npm install`。

1. 准备配置：
   ```bash
   cp config.example.json config.json
   cp .env.example .env
   ```
2. 在 Lark 建一个专用讨论群。每个发言者（含主席）在「群设置 → 群机器人 → 添加机器人 → 自定义机器人」里建一个机器人，设置名字和头像，**开启签名校验**。
3. 把每个机器人的 webhook 地址和签名密钥写进 `.env`，变量名对应 `config.json` 里各发言者的 `webhook.urlEnv` / `webhook.secretEnv`。`.env` 和 `config.json` 都不会进 Git。
4. 检查并发测试卡片：
   ```bash
   node src/cli.js check
   node src/cli.js send-test
   ```
5. 先在终端演练，再正式发到群里：
   ```bash
   node src/cli.js discuss "要不要把价格计算拆成独立服务？" --mock --dry-run   # 不调用模型，看流程
   node src/cli.js discuss "要不要把价格计算拆成独立服务？" --dry-run          # 调用模型，只打印不发群
   node src/cli.js discuss "要不要把价格计算拆成独立服务？"                    # 正式讨论
   node src/cli.js discuss --topic-file topic.md --mode brainstorm --rounds 3
   ```

## 配置说明（config.json）

| 字段 | 含义 |
|---|---|
| `mode` | `decision` 或 `brainstorm`，可用 `--mode` 覆盖 |
| `rounds` | `"auto"`（默认）：每轮评审在最后写「评审结论：继续讨论 / 没有意见了」，所有评审都写「没有意见了」就提前结束，否则一直讨论到 `maxRounds`。没有评审的方案讨论看主笔的「立场变化」是否都为「无」。写数字则是固定总轮数（含第 1 轮），1 到 20。brainstorm 里每多一轮是一个「盲审 → 修订」循环 |
| `maxRounds` | 自动轮数的上限，默认 20，最大 20。达到上限时主席会被告知「评审仍有意见」，汇总里列出卡住的问题 |
| `conversation` | 默认 `true`：每位参与者整场讨论在同一条会话里，记得自己说过的话，每轮只发新内容；`false` 时每轮都是新会话 |
| `limits` | 字数上限，可以只覆盖其中几项。方案讨论的默认值：要点 `brief` 150，第 1 轮方案 `propose` 1500，评审 `critique` 700，主笔修订 `review` 800，回应追问 `followup` 800，完整方案 `plan` 1800；作品打磨的默认值是 150 / 2200 / 900 / 1000 / 1000 / 2500。`tolerance` 默认 1.25，超过「上限 × tolerance」才要求压缩重写 |
| `items` | 默认 `false`。条目化发言（试跑中）：评审、主笔修订、代码核实、核对主文档、快问和改稿的挑刺写成一行一条的「【级别】问题 ｜改法 ｜依据 ｜影响」，写入时检查格式，见[条目化发言](#条目化发言试跑中)。网页上发起时可以按场打开 |
| `humanAsk` | 征询人：`enabled`（默认 `true`）、`maxAsks`（每次运行最多问几次，默认不限）、`pollMs`（等回答时读插话的间隔，默认 15000），见[征询人](#征询人) |
| `followUpMaxRounds` | 追问后重新讨论的轮数上限，默认 10 |
| `followUpContext` | 追问时参与者接着原会话（`resume`，默认）还是各开一条新会话（`fresh`），见[会话与追问](#会话与追问) |
| `sessionRetentionDays` | 会话保留天数，默认 7，过期后不能再追问 |
| `db.path` | 讨论记录库的位置，默认 `local/ai-storm.db`（相对 ai-storm 目录）；也可以用环境变量 `AI_STORM_DB`，见[讨论记录](#讨论记录) |
| `concurrency` | 同一轮里同时调用的模型数 |
| `ideasPerAgent` | brainstorm 每位主笔给几个脑洞，默认 3 |
| `participants[]` | 发言者：`id`、`name`、`role`、`persona`（角色设定）、`part`、`provider`、`model`、`effort`、`color`、`webhook`、`contextWindow`（上下文窗口 tokens，可选） |
| `part` | `lead`（主笔，默认）：出方案并多轮修订；`reviewer`（评审）：不出方案，每轮先给主笔的方案提意见，主笔再回应并修订。配置了评审时 `rounds` 至少为 2 |
| `chair` | 主席（brainstorm 时是主编），字段同上 |
| `models` | 可选，只给网页阵容用的额外模型：`id`、`name`、`provider`、`model`、`effort`、`color`、`contextWindow`。不在群里发言，不需要 `webhook`，见[选阵容](#选阵容) |
| `roleTemplates` | 可选，网页上的角色模板：`[{ name, persona, modes }]`，追加到内置模板后面，同名的覆盖内置的；`modes` 不写表示所有模式都列在前面 |
| `providers` | 模型接入方式，见下文 |
| `knowledge` | 可选，知识来源：`{ 名字: { path, index, description } }`；`local`（`local/knowledge`）总会带上，见[知识来源](#知识来源) |
| `dataTools` | 可选，查数据用的工具：`dir`（命令行工具目录，默认 `local/tools`）、`timeoutSec`、`maxOutputChars`、`mcpServers`（现成的 MCP 服务，各带 `allow`），见[数据工具](#数据工具) |
| `lark.interjection` | 插话读取：`enabled`、`chatId`（oc_ 开头）、`allowFrom`（只收这些 open_id 的消息，留空表示群里所有人） |

卡片标题颜色可选：`blue wathet turquoise green yellow orange red carmine violet purple indigo grey`。

## 模型接入

- **claude-cli**（当前在用）：通过本机已登录的 `claude -p` 调用，无工具、不保存会话，在临时空目录里运行。`model` 填 `opus`、`sonnet`、`haiku` 或完整模型 ID。
- **openai-compatible**（预留）：DeepSeek、Kimi、Qwen、OpenRouter 等。在 `providers` 里加一项，key 放 `.env`：
  ```json
  "deepseek": { "type": "openai-compatible", "baseUrl": "https://api.deepseek.com/v1", "apiKeyEnv": "DEEPSEEK_API_KEY" }
  ```
  然后在发言者上写 `"provider": "deepseek", "model": "deepseek-chat"`。
  发言者（或 provider）上的 `effort` 会作为 `reasoning_effort` 原样发出（`low` / `medium` / `high`）。有的网关不传就完全不思考，例如经 LiteLLM 网关接的 Gemini：它当评审时第 2、3 轮就会写「没有意见了」，所以接这类模型时要配上 `effort`。
- **anthropic-compatible**：Anthropic Messages 兼容接口（请求 `{baseUrl}/v1/messages`），例如阿里百炼的 `/apps/anthropic`。返回里的 thinking 块会被忽略，只取正文：
  ```json
  "bailian": { "type": "anthropic-compatible", "baseUrl": "https://<工作空间>.maas.aliyuncs.com/apps/anthropic", "apiKeyEnv": "BAILIAN_API_KEY", "maxTokens": 8192 }
  ```
  鉴权默认用 `x-api-key` 头，需要 `Authorization: Bearer` 时加 `"authHeader": "bearer"`。
- **新增其他类型**：在 `src/providers/` 实现 `complete({ model, system, prompt })`，返回 `{ text, model, durationMs, usage }`，再在 `src/providers/index.js` 的 `FACTORIES` 里登记。

## 在 Lark 群里发起讨论（watch）

```bash
node src/cli.js watch                 # 前台运行，Ctrl+C 停止（当前讨论结束后退出）
node src/cli.js watch --interval 60   # 改轮询间隔（秒）
node src/cli.js watch --dry-run       # 讨论只打印到终端，不发群（指令仍从群里读）
```

在讨论群里发：

| 指令 | 作用 |
|---|---|
| `/讨论 <议题>` | 方案讨论 |
| `/讨论 3轮 <议题>` | 固定总轮数（含第 1 轮）。不写时评审都没有新意见就结束，最多 20 轮 |
| `/讨论 仓库:pricing,fission@master <议题>` | 指定读哪些仓库；不写时调研员按议题自己定位，`仓库:无` 不读代码，见「代码上下文」 |
| `/脑洞 <题目>` | 脑洞风暴 |
| `/追问 [#编号] <问题>` | 追问一场讨论（默认最近一场），主席判断直接回答还是重新讨论，见「会话与追问」 |

- 议题可以换行写长一些；讨论进行中直接发的消息是插话，进行中再发的指令会在当前讨论结束后排队执行。
- 只响应 `lark.interjection.allowFrom`（或 `lark.watch.allowFrom`）里的 open_id，没配置时拒绝启动，避免群里任何人都能触发模型调用。
- 每隔 `lark.watch.intervalMs`（默认 30 秒）用 lark-cli 用户身份只读一次群消息。lark-cli 的应用是全公司共用的，偶尔会遇到短暂限流（99991400）：同一次读取里隔 3、6、10 秒重试，仍限流就等下一个间隔再读，不会加长等待，指令也不会丢（每次往回多读 2 分钟、按消息 id 去重）；单次开销约 0.1 秒 CPU。电脑睡眠时暂停，醒来后继续处理。
- 只处理 watch 启动之后的消息；同一台机器只能跑一个 watch（锁文件 `runs/.watch.pid`）。
- 运行状态写在 `runs/.watch.state.json`（阶段、当前议题、上次读群时间、上一场结果），klook-console「模型用量」页的「群内发起」面板读它，并可以在页面上启动、停止、强制停止；从页面启动时输出写到 `runs/.watch.log`。
- 停止：空闲时立即退出；讨论进行中会等这场讨论结束再退出，再发一次停止信号（或页面上的「强制停止」）立即退出。

## 代码上下文

先在 `config.json` 登记仓库。之后方案讨论默认都会先读代码：

```
/讨论 分析下 pricecenter 里 priceable 的缓存策略          # 不写仓库：调研员按议题自己定位
/讨论 仓库:pricing 要不要给批量定价加分布式锁？            # 指定仓库或组
/讨论 3轮 仓库:fission,price-center@develop 议题……         # 指定分支
/讨论 仓库:无 团队要不要统一用 pnpm？                      # 不读代码
```

```bash
node src/cli.js discuss "议题"                              # 自动定位
node src/cli.js discuss "议题" --repos pricing,fission@master
node src/cli.js discuss "议题" --repos none                 # 不读代码
node src/cli.js repos        # 列出登记的仓库和组，以及各仓库当前的分支与未提交改动
```

流程：讨论开始前，**调研员**（默认 Opus，用主席的机器人发言）只读查看代码，整理一份背景资料发到群里；之后所有主笔、评审和主席的提示词里都带着这份资料。调研失败时讨论不开始。

- **不写仓库时**：调研员拿到全部登记仓库的清单（别名、目录、描述、当前分支）和各组的参考资料，先按议题判断涉及哪些仓库。议题里写简称、服务名或中文业务词都可以，比如 pricecenter、价格中心。之后只读相关的仓库，背景资料开头会写「涉及的仓库」。议题和代码无关时，调研员只回「无相关代码」，讨论照常进行，不带背景资料。脑洞风暴不会自动读代码；不想要自动定位，可以设置 `research.auto: false`。

- 别名可以是单个仓库，也可以是组（展开成组里的所有仓库）。`@` 后面写分支、tag 或 commit；不写时读本机工作区，也就是当前分支加未提交改动，开场卡片会写明读的是哪个分支、有几个未提交改动。
- 写了 `@分支` 时，用 `git archive` 把那个版本导出到临时目录再读，不切换你本地的分支，结束后删除临时目录。只用本地已有的 ref（也会试 `origin/<分支>`），不会自动 fetch。
- 调研员用 `claude -p --restricted --tools Read,Grep,Glob` 运行：没有 Bash，不加载你的用户和项目设置与 Hook，文件工具只能读登记的仓库和参考资料目录。
- 资料里的源码坐标写作 `别名:仓内路径:行号`，讨论时可以直接引用。
- 背景资料会发给所有参与者，包括 Gemini 和 DeepSeek。

讨论中查代码：背景资料是讨论开始前一次性写好的，难免漏掉细节。所以讨论过程中还有两道补充：

- **主笔自己查**：用 claude-cli 的主笔默认带同样的只读工具（`Read,Grep,Glob`，`--restricted`，只能读这次的代码目录），背景资料没写到、或者对某个代码事实没把握时，可以自己去代码里查。评审和走 HTTP 接口的模型（Gemini、DeepSeek）没有这个能力。发言者上写 `"readCode": false` 可以关掉，`maxBudgetUsd` 可以限制单次发言的费用。查代码会让主笔每轮更慢、更贵。
- **核实两步（只在网页上选）**：网页发起方案讨论时，阵容下面的「核实员」可以选一个 claude-cli 模型（例如 Sonnet）。选了以后，「待核实的事实」先由核实员读代码写初稿，再由调研员（Opus）逐条审查、纠正：结论不对或坐标不支撑的改掉，查不到的改成「代码里找不到」，更正过的条目标「【已更正】」。**只有审查后的定稿发给主笔和评审**，初稿只在讨论记录里能看到。审查失败时初稿不发，这批问题留到下一轮；核实员失败时这次由调研员直接核实。不选时和原来一样，调研员直接核实。要选 Sonnet，先在 `config.json` 的 `models` 里登记它。本场无代码时核实员改为联网，见[联网搜集资料](#联网搜集资料)。
- **调研员核实**：每位参与者都可以在发言末尾写一节「**待核实的事实**」，每行一个能用代码回答的问题。下一轮开始前，调研员带着只读工具把这些问题查一遍，结果以「代码核实」卡片发到群里，并发给所有参与者（会话模式下每人只收到一次）；和背景资料冲突时以核实结果为准。有新核实结果的那一轮不会提前结束，主笔要先按结果修订。最后一轮提出的问题在主席写主文档前查掉，主席写文档时拿到全部核实结果。已经查过的问题不重复查，单次最多查 `research.factCheckMaxQuestions` 个，多出来的留到下一轮；核实失败时问题留到下一轮再试。
- **追问时**：原讨论带了背景资料的，追问时会重新准备代码目录（读本机当前的代码，可能和原讨论时有出入），主笔照样能查代码，调研员照样核实；原讨论的核实结果会保留。

配置：

```json
"repos": {
  "fission": { "path": "/Users/me/code/hotel/fission", "description": "酒店价格计算" },
  "price-center-job": { "path": "/Users/me/code/hotel/pricing/price-center-job", "description": "GTTD 批量定价任务", "docs": [] }
},
"repoGroups": {
  "pricing": { "description": "价格中心", "repos": ["price-center-job"], "docs": ["/Users/me/code/hotel/pricing/docs"] }
},
"research": { "provider": "claude-cli", "model": "opus", "effort": "medium", "maxChars": 16000 }
```

| 字段 | 含义 |
|---|---|
| `repos.<别名>.path` | 仓库的本机绝对路径，可以用 `~/` |
| `repos.<别名>.docs` / `repoGroups.<组>.docs` | 参考资料（目录或文件），调研员先看这里找线索，再到代码里核实。例如 insight 的 `domains/hotel` |
| `research.model` / `effort` | 调研员用的模型，只能是 claude-cli |
| `research.maxBudgetUsd` | 可选，单次调研的费用上限，超出就失败；默认不限制 |
| `research.timeoutMs` | 调研超时，默认 15 分钟 |
| `research.auto` | 方案讨论没写仓库时，是否让调研员从全部登记的仓库里按议题定位，默认 true |
| `research.maxChars` | 背景资料的字数上限，默认 16000；超出 1.5 倍会被截断 |
| `research.webhook` | 调研员用哪个机器人发卡片，默认和主席一样 |
| `research.factCheck` | 讨论中是否收集「待核实的事实」并由调研员查代码回答，默认 true |
| `research.factCheckMaxQuestions` | 单次核实最多查几个问题，默认 8 |
| `research.factCheckMaxChars` | 单次核实回答的字数上限，默认 4000 |
| `participants[].readCode` | 讨论中能否自己只读查看代码。不写时 claude-cli 的主笔为 true，其他为 false；只有 claude-cli 能设为 true |

## 联网搜集资料

只在网页上、方案讨论、**本场无代码**（写了「仓库:无」、没登记仓库，或调研员判断「无相关代码」），并且阵容里选了核实员时生效：

1. **主席判断**：讨论开始前，主席看议题，判断结论是否取决于外部事实（开源软件或云服务的行为与限制、公开标准、厂商文档、公开的行业数据）。不需要就照常讨论；需要就列出最多 6 个要查的问题和搜索关键词，这张卡片在讨论里能看到。
2. **核实员联网写初稿**：带 `WebSearch`、`WebFetch` 查资料，每条事实注明来源链接、适用版本和资料日期。
3. **调研员联网审查**：逐条打开来源核对，有错就改，查不到的改成「公开资料查不到」，更正过的条目标「【已更正】」。**只有审查后的定稿**作为背景资料发给所有参与者；审查失败时初稿不用，这场不带联网资料讨论。
4. **讨论中**：参与者可以在「待核实的事实」里问能用公开资料回答的问题，同样是核实员联网查、调研员联网审查后才发。

搜索关键词不带公司内部的系统名、服务名、项目代号、内部数据和人名（搜不到，也不该外发），这一条写在主席、核实员和调研员的提示词里。属于公司内部信息的问题，核实员直接回答「公开资料回答不了」。联网资料不算代码：主文档里仍然注明「本场无代码」。

工具名和字数上限可以在 `research.webTools`（默认 `["WebSearch", "WebFetch"]`）和 `research.webMaxChars`（默认 8000）里改。claude CLI 在 `--restricted` 模式下默认去掉 WebFetch，程序用 `--tools` 显式写上它。

## 数据工具

给调研员和核实员查日志、数据库、监控用的工具。主笔、评审和主席不直接用工具，只看到审查后的结论。

**在讨论里怎么用**（只在网页上的方案讨论，发起时勾选「数据工具」；群里和命令行发起的讨论不用）：

1. **开场查实时数据**：主席看议题，判断结论是否取决于现在的线上事实（数据量和分布、错误率和耗时、配置当前值、部署版本、某类记录有没有）。需要的话列出最多 6 个问题；核实员（阵容里选了的话）用数据工具写初稿，调研员同样带着工具，对照核实员的**查询记录**逐条审查纠正，只有定稿作为「实时数据」背景发给所有人。没选核实员时调研员直接查。主席判断不需要、或任何一步失败，这场就不带实时数据讨论。
2. **讨论中**：参与者可以把需要查数据才能回答的问题写进「待核实的事实」，下一轮开始前同样由核实员查、调研员审查。有代码时，代码核实也带上数据工具；本场无代码、选了核实员时，数据核实也能联网查公开资料。
3. **追问**：选择存在讨论状态的 `data` 里，追问照样带上；核实型追问可以用数据查。
4. **查数据的规则**写在核实员、调研员的提示词里：只读；每条结论写明工具和查询条件（环境、库表或服务、过滤条件、时间范围和时区）；`limit_reached`、`truncated` 写「至少」「不完整」；`NO_TOKEN`、`LOGIN_REQUIRED` 写「查不了：原因」，不能写成没有数据；「没查到」要附查询条件。
5. **记录**：卡片末尾附「查询记录」（工具、参数、结果大小、出错或被拒）；核实结果和开场数据在讨论状态里带 `toolCalls`；命令行工具的完整调用记录在记录库的 `tool_calls` 表，挂在这次运行上；用量事件 `call_finished` 记工具调用次数，开场查数据记 `data_researched`。

工具有两种来源：

- **命令行工具**：放在 `local/tools/`（整个 `local/` 不进仓库）。`tools.json` 登记工具，脚本放在同一目录，用什么语言写都行。程序起一个本地 MCP 网关（`src/tools/gateway.js`）把它们交给 claude CLI；调研员仍然不开 Bash，只能执行登记过的命令、填登记过的参数。
- **现成的 MCP 服务**：登记在 `config.json` 的 `dataTools.mcpServers`，写法和 Claude Code 的 `mcpServers` 一样（支持 `headersHelper`），另加 `allow` 列出允许调用的工具名，只放只读的。

`tools.json` 的一条：

```json
{
  "id": "room-stock",
  "description": "查某家酒店某天的房量；有酒店 id 和日期时用",
  "effect": "read",
  "command": ["node", "room-stock.js"],
  "params": [
    { "name": "hotel-id", "required": true, "description": "酒店 id" },
    { "name": "date", "description": "日期，默认今天" },
    { "name": "env", "enum": ["prod", "test"] }
  ],
  "timeoutSec": 60
}
```

| 字段 | 说明 |
|---|---|
| `id` | 小写字母、数字、横线；模型看到的工具名是 `mcp__storm__<id>` |
| `description` | 做什么、什么时候用，模型据此选工具 |
| `effect` | 只有 `read` 会开放给模型，其他值（如 `write`、`external`）跳过并在 `tools` 命令里列出 |
| `command` | 程序和固定参数，在工具目录里执行，不经过 shell。相对路径的程序（`./x.sh`）按工具目录解析 |
| `params` | `name`（不带 `--`）、`type`（`string` 默认 / `number` / `boolean`）、`required`、`enum`、`description`。调用时一律写成 `--name=value`，所以值以 `--` 开头也不会变成另一个开关；`boolean` 为 true 时只传 `--name` |
| `timeoutSec` / `maxOutputChars` | 单个工具的超时和返回给模型的输出上限，默认取 `dataTools.timeoutSec`（120）和 `dataTools.maxOutputChars`（20000） |

脚本的输出约定（推荐）：stdout 是数据；stderr **第一行写实际执行的查询**（补全后的条件），**最后一行写结果摘要**，例如 `{"rows":100,"limit_reached":true}`；退出码 0 是完成，其他是失败。网关把 stdout（超出上限时在行尾截断）、退出码和 stderr 的首行、末行一起交给模型，截断、失败、超时都写明，免得把不完整的结果当成完整的。

**只读边界**：
- 命令行工具只开放 `effect: "read"` 的；参数只认登记过的。
- MCP 服务只放行 `allow` 里的工具。claude CLI 在 `--restricted --strict-mcp-config` 下运行，只加载这些服务；服务的其他工具模型能看到，但调用会被拒（记在 `permission_denials`）。
- 不开 Bash，读代码的工具照旧只能读登记的目录。

**调用记录**：命令行工具每次调用（参数、退出码、耗时、输出长度、是否截断、stderr 首末行）由网关写进 JSONL；带 MCP 的调用改用 `stream-json` 输出，程序从里面取出全部工具调用（含被拒的），放在返回值的 `toolCalls`。

命令：

```bash
node src/cli.js tools                                   # 列出命令行工具（含跳过的及原因）和登记的 MCP 服务
node src/cli.js tools call time-convert at="2026-11-11 08:30:00"   # 不经过模型直接执行，看返回给模型的内容
node src/cli.js tools try "列出 dbx 里的数据库连接" --model sonnet  # 模型带着全部工具回答，端到端检查网关、服务和登录态
```

`tools try` 每次记成记录库里的一次运行（`kind` 为 `tools-try`），回答和工具调用都在里面。MCP 服务要登录的（例如靠 cookie 的 `headersHelper`），登录过期时服务连不上，`tools try` 会如实报告；先刷新登录再试。

## 知识来源

给调研员、核实员读的业务知识（Markdown 目录），和数据工具一起用：先从知识里知道该查哪张表、时间列是什么时区、某类问题怎么排查，再去查实时数据。

- **登记**：`config.json` 的 `knowledge`，可以有多个来源，例如 insight 的 hotel 领域知识：

  ```json
  "knowledge": {
    "hotel": {
      "path": "/path/to/insight/domains/hotel",
      "index": ["knowledge/INDEX.md", "playbooks/INDEX.md", "business-index.md"],
      "description": "insight 的 hotel 领域知识与排查 Playbook（只读，由 insight 维护）"
    }
  }
  ```

  `path` 可以是绝对路径、`~/` 或相对 ai-storm 目录；`index` 是索引文件（相对 `path`），默认 `["INDEX.md"]`。
- **local 来源**：`local/knowledge`（不进仓库）固定登记为 `local`，放不适合进 insight 的内容：跨领域的、个人整理的、还在验证的、讨论里查实的结论。约定：`INDEX.md` 每篇一行（文档、讲什么、什么时候看），文档按 `_template.md` 写 frontmatter（`title`、`summary`、`status`、`updated`、`evidence`）。目前只手工维护。
- **怎么交给模型**：各来源的索引写进提示词（每个索引最多 12000 字，超出的部分提示用 Read 打开），目录用 `--add-dir` 放行，模型按需用 Read / Grep / Glob 打开具体文档。ai-storm 只读这些目录，从不写入其他来源。
- **读法写在提示词里**：先看索引；引用写「来源名:相对路径」；知识和代码、实时数据不一致时以实时证据为准，并写明不一致；不同来源冲突时两边都列出来，不替人挑一边。

```bash
node src/cli.js knowledge          # 各来源的目录、索引、文档数
node src/cli.js tools try "hotel 订单表的时间列是什么时区" --model sonnet   # 带着知识和数据工具回答
```

**在讨论里怎么用**：网页上发起方案讨论时勾选要带的知识来源（默认全选）。调研员的开场代码调研、核实员和调研员的核实与审查、开场查实时数据都会带上；参与者不直接读，只看核实后的结论。

## 记忆

跨讨论带着走的背景和结论，不用每次重新交代。分工作、个人、小说三个域，都是 Markdown 文件，默认在 `local/memory`（不进仓库；`config.json` 的 `memory.path` 或环境变量 `AI_STORM_MEMORY` 可以改）：

- `<域>/profile.md`：**档案**，你自己写（身份、偏好、长期约束……），ai-storm 只读。
- `<域>/conclusions.md`：**已确认的结论**，一行一条，带来源讨论和日期。只有你在结论页确认后才追加。

用法：

- **带上**：新建页的「记忆」里按域勾选，作品打磨的发起页也可以选。默认只带一个域（快问、小会、方案讨论带工作，脑洞风暴、改稿、作品打磨带小说），个人域要自己勾。选中的域把档案和最近的结论限长（每个域 4000 字，档案最多占一半，结论新的在前，放不下的旧结论会注明条数）放进共用的系统提示词，所有模型都能看到，包括走接口、读不了本机文件的模型；整场不变，缓存能命中。开场卡片列出这次带了哪些记忆。
- **存入**：方案讨论的主文档最后有「可存入知识库的结论」（主席提议，最多 5 条），快问和改稿的文档也有（回答或改稿的一方提议，最多 3 条；改稿提的是这部作品以后都要遵守的设定和文风约定）。结论页的「存入记忆」里逐条勾选、选好域，点「存入记忆」才写进 `conclusions.md`；同一个域里一模一样的不重复写，已经存过的标「已存入」。
- **查看和删除**：左边「记忆」标签页按域列出档案和结论，结论可以删除。档案在文件里改。
- 个人记忆会发给所选模型所在的服务；勾选个人域时新建页会提示。

## 主文档

讨论动辄几十轮，过程看不过来，所以每场讨论维护主文档，记录讨论的结果和最终形成的方案，让没看过讨论的人直接读懂：结论是什么、要拍板什么、接下来做什么。

- **写法**：主文档给人读，不是讨论记录的归档。
  - 先提炼再展开：每个部分开头先写这部分的结论，后面只用来支撑它。
  - 不堆碎点：相关的点合并成一个判断，写清因果、取舍和先后，不影响决策的删掉。篇幅没有硬性上限，确实压缩不了的可以写长，但要写成连贯的段落或有序步骤。
  - 同一件事只写一次。
  - 要拍板的事每条标【先定】（不定就没法开工或会做错）或【可后定】，按重要程度排序。
  - 细节进附录：核实证据和代码坐标、完整清单、逐项实现约定、不影响开工的细节分歧都放附录，正文只写结论和「详见附录《……》」。
- **讨论结束时**：主席读完整的讨论记录写初稿 → 主笔在各自的会话里对照讨论核对（漏掉重要信息、写错、把分歧写成定论、用了代号，以及碎点堆砌、重复、重点没排在前面）→ 有意见时主席逐条判断、修改 → 在讨论里发一条短消息（一句话结论和最需要拍板的事），全文在网页的「文档」页。主笔核对说「没有问题」的不发到群里。
- **追问之后**：改当前文档。被推翻的结论直接改掉；被新结论取代或已经不重要的内容删掉或压缩，重复的合并，不只往里加。重新讨论的要主笔核对；直接回答的由主席判断要不要改（只是解释文档里已有的内容就不改）。每一版都留在讨论状态的 `docs` 里，网页上能切换版本、和上一版逐行对比。
- **新开文档**：一份文档只讲一件事。讨论或追问分出了互相独立的方向（各自有结论、拍板项和下一步），主席可以把它新开一份文档，必须写清原因；从当前文档移过去的内容在当前文档里只留一句「见《……》」。网页「文档」页先选文档、再选版本，新开的文档标出从哪份分出、为什么。之后的追问改最近写的那份文档，主席能看到其他文档的标题和一句话结论。
- **变更记录**：不写进正文，由程序按各版的原因和主席的说明生成，在「文档」页最下面，导出时接在文末。
- **结构**：
  - 方案讨论：一句话结论、要点（最多 5 条，每条一句）、要拍板的事、问题、方案、考虑过但没采用的做法、风险与未核实的前提、下一步。
  - 脑洞风暴：一句话结论、要点、题目与要求、最值得写的脑洞（每个写完整，不只写编号：钩子、题材、主角和他想要什么、冲突或金手指、开篇场景、卖点和差异、主线走向）、可以组合的点子、被低估的点子、放弃的方向、下一步。
  - 作品打磨：一句话结论、要点、要作者拍板的事、原稿的问题、修改方案、保留不改的地方。修订版按主文档写。
- **附录**：网页「文档」页里和主文档一起显示；删掉附录，主文档也能独立读懂、能据此拍板。
- 文中不出现「方案 A」「评审 1」这些代号和轮次。
- **导出**：「文档」页每一版都能导出 Markdown（正文、附录、变更记录）。
- **按新写法重写**：`node src/cli.js doc <编号> --rewrite` 让主席把各份文档的最新一版按现在的写法重写成新的一版：不加新结论，只提炼、合并、删重复、把细节移进附录，独立的方向可以拆成新文档；会话没过期时主笔核对。只打印到终端，不发群。
- **旧讨论补写**：改造之前的讨论只有汇总。`node src/cli.js doc <编号>` 让主席读全部讨论记录、原来的汇总和每次追问写一份，主笔核对；只打印到终端，不发群。也可以直接追问：重新讨论后会补写一份。

## 会话与追问

**会话**：每位参与者（主笔、评审）整场讨论在同一条会话里，模型记得自己之前说过的话。

- 每轮只发新内容：别人的最新方案、评审意见、新的插话。自己的上一版不再重贴，身份和规则只在第一条消息里说。
- 评审从第 3 轮起先跟进自己上一轮的意见，逐条标明「已解决 / 被合理反驳 / 仍未解决」，再提新问题。
- 接入方式：
  - claude CLI 第一次用 `--session-id`，之后用 `--resume`。工作目录固定为 `~/.cache/ai-storm/claude`，所以会话文件在 `~/.claude/projects/-Users-…-cache-ai-storm-claude/`。
  - HTTP 接口没有会话，由程序把之前的往来作为历史消息带上。
- 会话前缀固定，缓存命中率随轮数上升，实测第 3 轮以后约 50%–80%。
- 主席和调研员不用会话。主席写主文档时开一条临时会话，按核对意见修改时不用再发一遍讨论记录。

**追问**：每场讨论有编号，开场和结束卡片上都会显示，例如 `#12`。讨论结束后在群里发：

```
/追问 如果大促只剩三周，方案要怎么调整？        # 追问最近一场
/追问 #12 换成按商家分库呢？                   # 追问指定的一场
```

```bash
node src/cli.js followup "问题"            # 命令行，默认最近一场
node src/cli.js followup --run 12 "问题"
```

主席先判断怎么处理：

- **直接回答**：追问是澄清、解释，或者讨论记录里已经有答案。只调用一次主席。
- **按裁决定稿**：你在对分歧做选择，例如「按方案 A」「第 1 条按 B，第 2 条不做」。主席写出「按哪个方案定稿」和逐条复述的「人的裁决」：选的是某个方案时，由那位主笔按裁决写定稿；选择不对应单个方案时，由主席按裁决合并。不再经过评审，主文档的方案部分标「定稿（按人的裁决，未经评审）」，已裁决的分歧从待拍板里移走。主席没写清选哪个方案时按重新讨论处理。
- **核实**：你要求查证某些事实。主席列出「要核实的问题」，有代码时由调研员（选了核实员时先核实员答、调研员审查）读代码查，本场无代码但能联网时联网查；查完主席把结论合进主文档，不进入多轮讨论。不能核实的讨论（没代码也不能联网）不提供这个选项。
- **重新讨论**：追问带来新的约束或信息、质疑结论或要求换方向。主席写一段「给参与者的说明」，主笔在**原来的会话**里回应追问并修订，之后照常「评审提意见 → 主笔修订」，直到评审没有新意见（最多 `followUpMaxRounds` 轮）。评审会收到追问原文作为「本次讨论范围」：追问里已经拍板的决定不再质疑，范围外的问题不提、也不算【阻断】；主席的说明只给主笔，不给评审，以免评审被主席的判断带偏。最后主席把结论改进[主文档](#主文档)，在讨论里说明追问的结论和文档改了哪里。

**追问的会话：接着原会话还是新开**（`followUpContext`，默认 `resume`；网页上每次追问可以单独选）：

- **接着原会话（resume）**：参与者在原来的会话里接着聊，记得之前的推理细节，但会话越来越长。
- **新会话（fresh）**：每位参与者开一条新会话，第一条消息由程序拼出讨论现状：现在的主文档、自己和其他主笔目前的方案、阻断原文存档、讨论中人的全部插话，以及按预算（参与者窗口的 40%）从新到旧放入的核实结果。原议题和背景资料在系统提示词里。换下来的旧会话记在讨论状态的 `retiredSessions` 里，到期一起清理。这次追问里没发言的参与者（例如直接回答、核实）换回原会话。
- 每次追问记下用的是哪种（`followUps[].context`，`run_finished` 里也有），方便对比两种方式的结论质量、费用和上下文占用，再定默认值。群里的 `/追问` 和命令行用配置里的默认值。

讨论状态存在记录库里（`discussions.state`）：会话、各方最新方案、讨论记录、之前的追问、主文档的各个版本、阻断存档、讨论中的插话。每次追问是这场讨论下的一次运行，发言和用量单独记。

几点规则：

- 会话保留 `sessionRetentionDays` 天（默认 7），从最后一次更新算起。过期后删除 Claude 会话文件，清空讨论状态里的对话记录，这场讨论就不能再追问了。发言、主文档等讨论记录不受影响。
- dry-run 和正式讨论分开找「最近一场」。
- `--mock` 演练不编号、不保存会话。

## 本地网页

```bash
node src/cli.js web            # 打开 http://127.0.0.1:8790/
node src/cli.js web --mock     # 演练：不调用模型，修订版不能写回
```

左边「讨论」列出**全部讨论**：群里 `/讨论`、`/脑洞` 发起的，和网页上发起的，标着「群里 / 网页 / dry-run」。讨论记录都在记录库里，网页直接查库，所以不管讨论是 Lark 监听进程还是网页自己跑的，都能实时看。

- **发起**：点「＋ 新讨论」，先选档位，写问题，需要时在「材料」框里贴原文（章节、日志、文档片段，最多 30000 字，不占议题的 8000 字上限，所有参与者都能看到）。仓库、数据与知识、轮数、[阵容](#选阵容)收在「高级选项」里。**网页上发起的讨论只在网页上，不发到群里**。网页上的讨论一场一场排队。
  - **快问**（默认）：一位回答、一位挑刺，最后由回答的一方定稿，共 3 次模型调用。结果是一份短文档：回答、你可能没考虑到的、需要你补充的、下一步、可存入知识库的结论。不会开始前反问，缺的信息写在结果里，用追问补充。快问可以读代码：「高级选项」的代码仓库不写时，调研员先判断问题涉及哪些登记的仓库再读（不涉及就只回「无相关代码」，发一张「本场无代码」卡片，不带代码回答），写别名就读这些，写「无」不读；读了代码就多一次调用、多几分钟，背景资料进所有人共用的提示词。调研失败不影响回答。快问不查实时数据；勾了知识来源时，索引写进提示词，能读本机文件的模型（claude 命令）还能打开正文。
  - **小会**：方案讨论的轻量版，两位主笔、一位评审，最多 3 轮。
  - **方案讨论**：完整流程，可以读代码（不写仓库由调研员按议题定位，写「无」不读代码）、查数据、核实事实，可以选轮数。
  - **脑洞风暴**：主笔发散、评审盲审、多轮修订。结束后在「文档」页可以「带着结论快问」或「带着结论讨论」：结论放进材料框，接着往下想。
  - **改稿**：贴一章原文（「章节原文」框，最多 30000 字），可选写要求和「设定与上下文」（人物、世界观、前情，最多 20000 字）。一位改稿、一位对照原文挑刺、改稿的一方定稿，共 3 次模型调用。结论页有修改说明、没采纳的意见、逐段对比（改得多的段落上下分开显示原文和新文）和修改稿全文，「复制修改稿」一键复制，不写回墨稿。修改稿比原文短很多或输出被截断时，会发一张提醒卡片。追问（例如「第三段再收一点」）由改稿的一方回答并更新修改稿。
- **快问的追问和升级**：快问的追问不经过主席分流，固定由回答的一方只看现在的快问文档直接回答，再把结论改进文档。觉得不够深时点结论页的「升级为讨论」：问题照搬，快问结果和原来的材料放进材料框，默认选小会，确认后开始。快问过了保留期不能再追问，也可以这样接着讨论。
- **状态条**：讨论页顶部固定显示状态、进行中是第几轮和谁在写、结束原因（僵局、评审分歧、到轮数上限用警示色）、核实了几个问题、最后仍提阻断的评审数。点阻断数：结束后跳到结论页的阻断区块，进行中跳到最新一轮评审。
- **结论**（方案讨论）：结束后打开讨论默认进这一页。把最新一版[主文档](#主文档)按段切开，依次是一句话结论、要点、要拍板的事（标题含「拍板」的小节排在前面，【先定】/【可后定】标成标签）、下一步、风险，下面是结束状态和阻断区块；有几份文档时可以切换，「看全文」跳到文档页。主文档缺了要点、要拍板的事或下一步任何一段，就显示全文并提示「未能提取」，不硬切。没有主文档的旧讨论进「结论（旧版汇总）」页。
- **讨论**：按轮折叠，每次追问另起一段。开场之后依次是「背景」（调研、资料、追问判断）、「第 N 轮」、「收尾」（核对主文档、主文档）；插话归在它前一条所在的轮，开场卡和结束卡不折叠。轮头显示「评审 X/Y 没有意见」和「N 位提了阻断」，展开后每位发言者先露出要点，详细内容仍然折叠。打开时只展开最新一组，可以全部展开 / 收起，或从「跳到…」直接跳到某一轮。进行中新的一组自动展开；你收起的组不会被强行展开，只在组头显示未读条数。
- **阻断的统计口径**：网页只认行首的【阻断】（列表项、序号、加粗之后紧跟【阻断】），「本轮没有【阻断】」这类否定句和在【建议】里顺带提到的不算；评审写了「没有意见了」的也不算仍提阻断。解析不出评审结论的标「未识别」，不当成 0。阻断区块统计最后一次有评审发言的运行，每位评审看最近一次发言（失败卡片不算）；以前提过、最近一次没再提的折叠为「后来没再提」，不代表已经解除。之后还有按裁决定稿的追问时，标题改成「裁决前评审仍提的阻断」。流程控制（收敛、熔断）仍用原来的判定，所以以熔断或到上限结束时，网页列出的阻断可能比程序认定的少，以结束原因为准。这些都是网页读库时算的，不改记录，群卡片也不变；解析不出评审结论、主文档切不开时，网页进程的日志里各记一行。
- **条目**：打开了[条目化发言](#条目化发言试跑中)的讨论，卡片要点下面列出条目标题（级别标签 + 问题），点开看改法、依据和影响；依据是「推断」的标成未核实，代码坐标可以一键复制。没有要点的发言（例如代码核实）条目在前、原文折叠。轮头另外显示阻断条数（只数正文里的行首【阻断】）、采纳 / 不采纳数和代码核实推翻了几处，后两项要这一轮相关发言全部解析成功才给数字，否则标「未识别」；旧讨论不显示。要点里说的阻断数和正文对不上时，卡片标「要点与条目不一致」，以正文为准。讨论页工具条的「只看阻断」只留有行首阻断的发言和阻断条目。结论页的阻断区块按条目显示，可以「复制为 Markdown」转给别人。
- **插话**：讨论进行中可以在页面底部插话，下一轮开始时交给所有模型。群里的讨论也可以从网页插话，群里会同时出一张主席发的「主持人插话」卡片，大家知道模型在回应什么。
- **数据与知识**：方案讨论可以勾选「数据工具」和知识来源，见[数据工具](#数据工具)和[知识来源](#知识来源)。
- **追问**：讨论结束后可以在页面底部追问，主席判断直接回答、按裁决定稿、核实还是重新讨论；旁边可以选这次接着原会话还是用新会话。群里的讨论在网页上追问时，追问过程照样发到群里。
- **文档**：每场讨论的「文档」页显示[主文档](#主文档)和附录；有几份文档时先选文档，可以切换版本、和上一版逐行对比、导出 Markdown（改了的行标出行内差异，大段没变的折叠），下面是追问记录和每次追问改到了第几版。
- **找和整理**：搜索框搜编号、议题和全部发言内容；可以按模式（方案 / 脑洞 / 打磨）和时间（最近 7 / 30 / 90 天）筛选。讨论页右上角可以「归档」（不在列表里，勾「只看归档」能找到，可以取消归档）和「删除」（发言、主文档、追问、用量记录和 Claude 会话文件一起删，不能恢复；进行中或排队中的不能删）。
- 进行中的讨论如果跑它的进程退出了、没写结束记录，显示「失败」，并按情况给一个接着跑的按钮：
  - **从断点续跑**（方案讨论、小会、脑洞风暴、作品打磨）：讨论在开场调研之后、每一轮评审和修订跑完、轮次结束之后各存一次断点（会话、方案、讨论记录、核实结果、还没核实的问题、熔断计数、插话读到哪里），存在记录库的 `checkpoints` 表，正常结束后删掉。续跑从最近的断点接着跑，最多重跑一轮；发言接着记在原来那次运行名下，先发一张「续跑」卡片，断点之后、中断之前发出的发言标成作废（灰色，不算进阻断和问题追踪）。Claude 的会话由 claude 命令自己保存，可能多出中断那一轮的半截内容，以续跑后的为准。群里发起的讨论续跑时照样发到群里。
  - **重新跑**（快问、改稿，或者还没存下断点就断了）：用原来的问题、材料和阵容另起一场，编号是新的。
  - **重新排队**：排队时网页重启了、根本没开始的，用原来的参数在同一个编号上重新排队。网页发起时就把发起参数存进了 `checkpoints` 表。
  - **重新追问**：追问中断了，原讨论不受影响（状态在追问开始前就存着），用同一个问题再追问一次。
  - 不会自动续跑，要你在页面上点。重启网页前最好看一眼左侧有没有「进行中」「排队中」的讨论；第一次按 Ctrl+C 只提醒，再按一次才强制退出。

### 选阵容

网页上发起讨论或打磨时，每场自己定：

- **参与者**：每一位选一个模型，选「主笔」或「评审」，写角色和角色设定。可以从角色模板套用，套用后还能改。同一个模型可以选多次，扮演不同角色，名字后面加序号区分，比如「Claude Opus（2）」。2 到 8 位，至少 1 位主笔。
- **主席 / 主编**：选用哪个模型汇总、写主文档（打磨还写修订版）。
- **恢复默认**：回到 `config.json` 里配好的参与者和主席，打磨和脑洞风暴分别用 `personas.refine`、`personas.brainstorm` 换过的角色。
- 每个模式上次用的阵容记在这台电脑的浏览器里，下次默认沿用；配置里删掉了其中的模型时退回默认。

可选的模型是 `config.json` 里的每位参与者，加上 `models` 里只给网页用的模型；主席用的模型不在其中时也会列出来。

阵容存在这场讨论的状态（`lineup`）里，追问时照原样用，之后改配置也不影响。自选阵容的讨论只能在网页上追问；群里不写编号的 `/追问` 不会落到它上面。

**群里和命令行不受影响**：`/讨论`、`/脑洞` 和 `node src/cli.js discuss` 仍然用 `config.json` 里固定的参与者，每位用自己的机器人发言。

插话的实现：网页把插话写进记录库，挂在正在进行的那次运行上，跑这场讨论的进程（Lark 监听或网页）每轮开始时读新增的，和群里的插话合在一起。

### 作品打磨

个人创作用，不发到 Lark。先启动墨稿（Work Console 的墨稿模块，或在 novel-idea 里 `npm run dev`）。

1. 左边「脑洞 / 梗概 / 总纲 / 细纲」列出墨稿里的内容，点一项看现在的版本和背景（定位、素材、墨稿评委已经给过的意见、已写的章节）。细纲按卷每 10 章一段列出（例如「明日热榜 · 第一卷 第 1–10 章」），背景里带着总纲、本卷概要、本卷前后已写的章节和下一卷概要。
2. 可以写一句「这次想怎么改」，然后点「开始打磨」。
3. 流程同方案讨论：主笔各自诊断并给修改方案 → 评审提意见 → 主笔修订，直到评审没有新意见（最多 `maxRounds` 轮）→ 主编写主文档（修改说明：原稿的问题、修改方案、分歧和需要你拍板的问题），主笔核对 → 主编按主文档写出**完整修订版**。追问后重新讨论会重写修订版。
4. 「修订版」页逐处对比原稿（删掉的标红、新写的标绿）。确认后点「**写回墨稿**」才会改墨稿：
   - 脑洞、梗概直接覆盖原来那一条；原稿在「原稿」页和讨论状态里都留着。
   - 总纲连同分卷一起改：分卷按顺序对应，已经写了章节的分卷不能删。写回前墨稿会自动存一份历史版本，可以在大纲页恢复。
   - 细纲只改这一段里各章的内容（章名、概要、场景、出场人物、必须交付、推进、冲突、爽点、章末钩子），章号、章数和作者备注不动；修订版的章号对不上就拒绝写回。写回前同样存一份历史版本。
   - 讨论开始后你在墨稿里又改过这一项，写回会被拒绝，免得覆盖新内容。

默认阵容的角色按模式换：`personas.refine` 把四个模型换成「结构与人物 / 读者视角 / 市场与差异 / 逻辑与可持续」，主席换成「主编」；`personas.brainstorm` 换成主笔「类型反转 / 人物欲望」、评审「挑剔读者 / 市场与差异」，主席也换成「主编」。另有「爽点与钩子」模板可以在页面上套用。打磨细纲另记一套阵容：模型、主笔 / 评审和主编沿用作品打磨的，角色按座位顺序换成「节奏与爽点 / 追更读者 / 场景与可写性 / 连贯与账目」，也可以在 `personas['refine-chapters'].<发言者 id>` 里指定。细纲的评审门槛也不同：脑洞、梗概、总纲是在搭架子，具体数字和执行细则最多算建议；细纲是写正文前的最后一层，和前后章节、本卷概要、总纲对不上（时间线、数字账、出场顺序），某章没推进没爽点、主角连着被动、章末钩子断档、场景空到写不出来，都算阻断，文笔和总纲层面的问题仍只算建议。开始前可以在页面上改阵容，见[选阵容](#选阵容)。模型通道和方案讨论共用同一套配置。

所有讨论共用一套编号；群里的 `/追问`（不写编号时）不会落到打磨讨论上，打磨只能在页面上追问。修订版和写回记录在讨论状态里。

配置项：`novel.baseUrl`（墨稿地址，默认 `http://127.0.0.1:3000`）、`web.port`（默认 8790）、`web.host`（只能是本机地址，页面没有登录）。

## 条目化发言（试跑中）

诊断和评审类发言把每个问题写成一行条目，人能很快看出问题、怎么改、依据是什么。默认关着，配置 `items: true` 打开，或者在网页新建页的「高级选项」里按场勾选（追问沿用发起时的设置）。

- **格式**：`- 【级别】问题 ｜改法：… ｜依据：… ｜影响：…`。「【级别】问题」必写，后面三段按这个顺序用全角竖线隔开，没有的段整段省掉。条目写在加粗小节里（评审按方案代号分组，挑刺写在「**问题**」下），不直接接在要点后面；要点里不写【阻断】【建议】标记，只用文字说。
- **各阶段的级别**：评审和挑刺 【阻断】/【建议】，【阻断】必须带改法和依据；主笔修订「【改】原来 → 现在 ｜依据」，回应评审写【采纳】/【不采纳】，不采纳必须带依据；代码核实 【确认】/【推翻】/【查不到】，依据是源码坐标，审查更正过的在级别后加【已更正】；核对主文档 【漏】/【错】/【不清】。「评审结论」行和「立场变化」段不变，收敛判定照旧。
- **依据**：只有四类：代码坐标 `仓库别名:路径:行号`、「第 N 轮核实第 K 条」、资料（联网或实时数据）、「推断」。没有实据写「推断」。依据不计入字数上限（从「｜依据：」剔到下一个「｜」），压缩时就不会先被删掉。
- **写入时检查**：评审缺「评审结论」行、【阻断】缺改法或依据、主笔缺「立场变化」、超字数（依据不计），有任何一项就合并成一次重写，要求只补缺项或压缩、内容和立场不变（代替原来单纯的压缩重写）。重写后评审结论变了、或行首【阻断】变少了，就用第一次的原文；仍不合格照常发布。每次检查在用量记录里记一条 `reply_check` 事件（`ok` / `rewritten` / `kept-original` / `still-failing` / `rewrite-failed`），试跑时用来算重写率。
- **解析**：网页读库时解析（`modes.js` 的 `parseItems`），不落盘，旧的「【阻断】问题 → 后果 → 怎么改」也能拆出问题、后果和改法。解析不出的卡片照原样显示。群卡片显示的是原文。

### 问题追踪

条目化打开的方案讨论和作品打磨里，每个问题有编号，跨轮跟踪它的经过。快问、改稿、脑洞风暴不编号；旧讨论照原来的方式显示。

- **编号**：`Q评审号-序号`，例如 `Q1-3` 是评审 1 整场的第 3 个问题，跨轮、跨追问累计。评审发言过完写入检查之后、发布之前，由程序写在【阻断】【建议】的级别后面（只写正文，要点和完整方案不编号），所以库里、群卡片和主笔看到的是同一份带编号的文本。模型不自己编号：评审写了自己之前的编号就保留（仍坚持的旧问题）；写了别人的、不存在的、或同一条发言里重复的，剥掉按新问题重编，不触发重写。每次编号记一条 `issue_ids` 事件（沿用、新分配、剥掉的个数和原因）。
- **评审**：只要提过还没解决的阻断，任务里就附一张「你提过、还没解决的问题」清单，由程序从发布的版本生成（会话里存的是模型的原始回答，没有编号），每条附上主笔之后的处理（称采纳 / 不采纳 / 未回应）。仍坚持就写原编号，新问题不写编号。对其他评审的阻断表态写在「**对其他评审的阻断**」下面：`- 【不同意】Q2-1 ｜依据：…` 或 `- 【补充】Q2-1 ｜依据：…`。
- **主笔**：回应写 `- 【采纳】Q1-3 ｜改法：…` 或 `- 【不采纳】Q1-3 ｜依据：…`。引用错了或漏回应不拦截，页面如实标出。
- **页面**：结论页（讨论进行中也有）的「问题追踪」每个编号一条时间线：第几轮谁提出（哪个方案）→ 其他评审补充或不同意 → 主笔称采纳 / 不采纳 → 原评审仍坚持，或之后没再提（分称采纳后、不采纳后、未回应后）。阻断默认展开，建议折叠；引用了不存在或别人编号的单独列为「引用无效」。措辞保持中性：「称采纳」是主笔自己说的，「没再提」不代表已经解决。卡片上的条目也显示编号。

## 插话

把 `lark.interjection.enabled` 设为 `true` 并填上讨论群的 `chatId`。群 ID 可以这样查：

```bash
lark-cli im +chat-search --query "<群名>" --as user
```

讨论中你在群里发的消息，会在**下一轮开始时**交给所有模型，主席写主文档时也会看到。也可以在[本地网页](#本地网页)上插话。读取用的是 lark-cli 的用户身份，只读这个群、只读讨论开始之后的消息，机器人自己的发言不算插话。`--no-interject` 可以临时关闭。

## 征询人

人跟不上讨论的速度，很少主动插话，讨论跑偏要等结束才知道。所以方案讨论、脑洞风暴和作品打磨里，**每一轮结束后主席判断要不要暂停讨论、向你提问**（第 1 轮之后也会判断，脑洞风暴第 1 轮之后改为请你挑脑洞，见[脑洞风暴](#ai-storm)；最后一轮不问，问了也没人回应）：

- **什么时候问**：需求没写清、各方理解不一致；方向卡在几个都说得通的选项之间，取舍取决于你的偏好或资源；讨论在偏离你说过的要求；主笔和评审僵住了只有人能裁决。模型能自己查到的事实、写到主文档里再拍板也来得及的细节、你已经回答过的，都不问。
- **怎么问**：主席发一张「❓ 讨论暂停，等你回答」卡片，最多 3 个问题，每个都写明要你定什么、有哪些选项、为什么现在问。网页讨论页顶部标「等你回答」，底部换成回答框；列表上也标出来。
- **一直等**：讨论停在这里，直到你回答，没有超时。在网页回答框里回答，或者在群里直接回复（走插话通道，下一条消息就是回答）。不想定就点「按你们的判断继续」。
- **回答之后**：回答当作插话交给所有模型，带上问的是什么，主笔必须先回应，这一轮不会提前结束；主席写主文档时也看得到。问答存在讨论状态的 `asks` 里，进程中断后续跑时，还没回答的问题接着等。
- **次数**：默认不限，问不问全由主席判断。真觉得问得太勤，可以配 `humanAsk.maxAsks` 限制每次运行（发起一次、每次追问各算一次）最多问几次，用完就不再判断。没有插话通道时（命令行没开插话）不问。
- **配置**：`humanAsk.enabled`（默认 `true`）、`humanAsk.maxAsks`（默认不限）、`humanAsk.pollMs`（等回答时多久读一次插话，默认 15000；群里的讨论每次都要调 lark-cli，别设太小）。

每轮的判断是主席多一次调用，只带最新方案、这一轮的意见、你说过的话和问过的问题。

## 讨论记录

全部记录存在一个 SQLite 文件里，默认 `local/ai-storm.db`（`local/` 不进仓库），位置可以用 `db.path` 或环境变量 `AI_STORM_DB` 改。Lark 监听、网页、命令行和数据工具网关是不同的进程，同时读写这个文件（WAL 模式，写冲突时最多等 5 秒）。

| 表 | 内容 |
|---|---|
| `discussions` | 一场讨论一行：编号、模式、议题、渠道、是否 dry-run / mock / 会话已过期、创建和更新时间、归档时间，`state` 是完整的讨论状态（JSON） |
| `executions` | 一次运行：讨论本身（`discussion`）、一次追问（`followup`）或一次 `tools try`；开始结束时间、状态（`running` / `done` / `failed`）、出错原因、进程号、结果（JSON） |
| `posts` | 发言：网页和群里看到的每张卡片 |
| `events` | 用量事件，见[用量与上下文记录](#用量与上下文记录) |
| `interjections` | 网页插话 |
| `tool_calls` | 命令行数据工具的调用记录 |

删除讨论时，它的运行、发言、用量、插话和工具调用一起删掉。编号是库里最大的编号加 1。`runs/` 只剩 Lark 监听进程的运行文件（`.watch.pid`、`.watch.state.json`、`.watch.log`）。

## 用量与上下文记录

每次运行的用量事件写进记录库的 `events` 表（`data` 列是整条事件的 JSON），供 klook-console 的「模型用量」页面读取：

| 事件 | 内容 |
|---|---|
| `run_started` | 议题、模式、轮数、参与者与主席（provider、配置的模型、`contextWindow`）、进程号、是否 dry-run / mock |
| `call_started` | 谁开始调用、哪个阶段、第几轮 |
| `call_finished` | 实际模型、输入/输出 tokens、上下文窗口、上下文占用（`contextTokens`、`contextKind`、`contextPct`，见下文）、费用、耗时、是否被截断；带工具的调用还有回合数 `turns`。`retry` 为 `compress` 是压缩重写，为 `error` 是临时故障后的重试 |
| `call_failed` | 失败原因；`willRetry: true` 表示是临时故障，马上重试一次 |
| `fact_checked` | 第几轮做了代码核实、查了几个问题；用了核实员时还有 `reviewed: true` 和审查更正了几条 `corrections` |
| `doc_written` | 主文档写到第几版、原因、字数、附录数、主笔核对结果 |
| `doc_failed` | 主席重写一次后仍没写出主文档，程序发了兜底卡片 |
| `web_researched` | 开场联网搜集完成：查了几个问题、审查更正了几条 |
| `chair_budget` | 主席这次调用的输入预算和装填结果，见[主席输入预算](#主席输入预算) |
| `run_finished` / `run_failed` | 本次用量合计和结束原因 `ending`，或错误 |

结束原因（`ending`，也存在讨论状态里）：`converged`（提前收敛）、`deadlock`（熔断一：主笔和评审各自坚持）、`dissent`（熔断二：一位评审独自坚持）、`max`（到轮数上限仍有意见）、`fixed`（按固定轮数结束）、`answered`（追问由主席直接回答）。熔断见[收敛与熔断](#收敛与熔断)。追问重新讨论时写这次追问讨论的真实结束原因。

**上下文占用**：claude CLI 带工具（读代码）时一次调用会跑很多回合，返回的输入 tokens 是各回合的累计值，可能远超窗口，不能直接除以窗口。所以另记一个占用：

| `contextKind` | 适用 | `contextTokens` |
|---|---|---|
| `exact`（准确值） | HTTP 接口，以及只跑了 1 个回合的 claude CLI 调用 | 这次实际送进模型的输入 tokens |
| `lower`（下界） | 多回合的 claude CLI 调用 | max(累计 ÷ 回合数, 缓存写入, 这条会话上次已知的占用) |

卡片页脚显示「上下文 39%」，下界显示「≥12%」，超过 50% 带 ⚠️；多回合调用的输入写成「累计输入 X（N 回合）」。结束卡片列出每位参与者最近一次发言的占用。klook-console 的「上下文峰值」也按这个口径算，旧记录按同样的规则估。

上下文窗口的来源：claude CLI 会返回实际模型和窗口大小；OpenAI 兼容接口在没写 `contextWindow` 时会查一次 `{baseUrl}/models`（LiteLLM 网关返回 `max_input_tokens`）；Anthropic 兼容接口（百炼）查不到，需要在发言者上写 `contextWindow`。

缓存：三种接入方式都会记录缓存读取（`cacheReadTokens`）和写入（`cacheWriteTokens`），卡片页脚显示命中率。

费用：claude CLI 自带费用，但 `--resume` 续接会话时返回的是整条会话的累计值，所以每条会话记下上次的累计值（讨论状态里的 `cliCostUsd`），只计差值；续接一条没记过累计值的旧会话时按 `claude-cli` 上配置的 `pricing` 估算（`cacheWriteRatio: 2` 对应 Claude Code 的 1 小时缓存写入）。LiteLLM 网关从响应头 `x-litellm-response-cost` 读取；接口不返回费用时（百炼），按 provider 上配置的价格估算，事件里带 `costEstimated: true` 和原币金额，看板上显示为「≈」：

```json
"bailian": {
  "type": "anthropic-compatible",
  "pricing": {
    "deepseek-v4.1-flash-1017": {
      "currency": "CNY", "usdRate": 6.7,
      "inputPerM": 2, "outputPerM": 8, "cacheReadRatio": 0.1,
      "offPeak": { "from": "22:00", "to": "08:00", "timezone": "Asia/Shanghai", "inputPerM": 1, "outputPerM": 4 }
    }
  }
}
```

单价是每百万 tokens；`cacheReadRatio` / `cacheWriteRatio` 是缓存命中 / 写入按输入单价的比例；`offPeak` 是闲时价格；`longContext` 是长上下文档（`aboveTokens` 之上，按一次调用的完整输入算，例如 `{ "aboveTokens": 272000, "inputPerM": 0.48, "outputPerM": 1.8 }`，超过就整次按这一档，缓存比例沿用）；`usdRate` 是 1 美元折多少原币，用来和其他模型一起按美元汇总。上面的数字来自百炼官方价格页和上下文缓存说明（2026-11）。

## 出错时怎么处理

- **临时故障重试一次**：超时、HTTP 5xx、连接中断，以及 claude CLI 报的 API 5xx / 529 过载，隔 5 秒（`retryDelayMs`）重试一次，主笔、评审、调研员、主席都适用。4xx、配置错误等不重试。
- **输出被截断**：OpenAI 兼容接口的 `finish_reason` 为 `length`、Anthropic 兼容接口的 `stop_reason` 为 `max_tokens` 时，记 `truncated: true`，卡片页脚标「输出被截断」。
- **主席写不出主文档**：换一条新会话重写一次，重写时[输入预算](#主席输入预算)减半；仍失败就由程序发一张「主席汇总失败 · 程序整理的结果」卡片，内容是各主笔的最终方案、每位评审最后提的阻断、还没核实的问题，不经过模型。讨论状态记 `docFailed: true`，之后可以用 `node src/cli.js doc <编号>` 补写。
- **主席判断不了追问**：按「重新讨论」处理，参与者直接回应追问，这次追问记 `triageFailed: true`。
- **代码核实连续失败**：同一批连续失败 2 次（每次已含一次重试），下一批条数减半，直到 1 条；没查的问题留在队列里，成功后恢复 `factCheckMaxQuestions`。

### 主席输入预算

主席写主文档、追问后更新主文档、补写主文档、判断追问，都要把讨论记录和核实结果拼进一次调用。讨论越长、追问越多就越长，所以按预算装填：

- **预算**：主席上下文窗口的一半，换算成字数（窗口 × 0.5 ÷ 每字 tokens 数）。重写主文档时再减半。
- **必须保留，不缩略**：各主笔的最终方案、现在的主文档（或上次汇总）、之前追问的回答、用户的全部插话、这次的追问。这些超出预算也照发。
- **按预算从新到旧放入**：讨论记录和核实结果。放不下时，较早的轮次只留每条发言的要点，较早的核实只留问题和回答开头 200 字；再放不下的更早部分整段省略。主席的提示词开头有一段「篇幅说明」，写明哪几轮被缩略或省略。
- **窗口和每字 tokens 数**从本场的调用里学：窗口取 CLI 或接口返回的值；每字 tokens 数取会话第一条（或无会话）、单回合、提示词不少于 2000 字的调用。都存在讨论状态的 `budget` 里，追问时接着用；没有这个字段的旧讨论从它的用量事件推出来。都不知道时按窗口 20 万 tokens、每字 2 tokens 估，宁小勿大。实测 Claude 约 0.9 token/字，Gemini 和 DeepSeek 约 0.5。
- 每次装填记一条用量事件 `chair_budget`：预算字数、必须保留部分的字数、是否超出、缩略和省略了几轮、几次核实。

按 1M 窗口算，目前最长的讨论（#2，约 24 万字记录加核实）也放得下，预算主要防的是窗口更小的主席模型和越追问越长的情况。

## 讨论规则补充

- **评审互见**：方案讨论和打磨里，评审从第 3 轮起能看到上一轮其他评审写在行首的【阻断】原文（只贴那几行，匿名；「本轮没有【阻断】」这类否定句不转）。**每一条都要表态**，对照主笔这一轮的方案核对：【仍成立】（还没解决，可以补充证据）、【已解决】、【不同意】（本来就不成立或不该算阻断，必须写依据）。引用照抄题目里的：开了问题追踪的用编号（Q2-1），没开的由程序标成「评审 N 第 K 条」。写完后程序检查，漏了表态或【不同意】没写依据，要求补写一次；补完还漏的照常发布，记一条 `reply_check` 事件。评审结论只按自己的问题写，对别人阻断的表态不影响自己的结论。脑洞风暴的盲审不互见。
- **已经解决的阻断不再提**：评审后来自己写了「没有意见了」，或者人在追问里按裁决定稿过，之前的阻断就算已经解决。评审的任务里会列出最近 8 条已经解决的阻断，要求不要再提；只有认为当时的解决办法本身有问题时才能重提，问题开头写「重提」，并给出原来的解决办法错在哪里、新的依据。
- **收敛与熔断**：见下一节。
- **本场无代码**：方案讨论没带代码背景时（写了「仓库:无」、没登记仓库，或调研员判断「无相关代码」），开场卡片和结束卡片都写明「本场无代码」，主席在主文档里把涉及代码现状的结论标为未核实。

### 收敛与熔断

只在自动轮数（`rounds: "auto"`）、有评审的方案讨论和打磨里生效。程序只看确定性的信号：主笔的「无变化」标记、评审有没有【阻断】、评审结论，不做语义判断。

- **「无变化」标记**：主笔这一轮没改方案时，「【完整方案】」下面只写「无变化」三个字，程序沿用上一版。没写这个标记、发言失败、或者写了别的内容，都算改了。
- **直接结束**：评审都没有阻断，并且这一轮没有新的核实结果、没有新插话（原来的提前结束）。
- **修订后结束**：评审都没有阻断，但有新核实结果或新插话：主笔先回应；全部「无变化」就结束，有人改了方案就再给评审看一轮。
- **熔断一（`deadlock`）**：主笔连续 2 轮全部「无变化」，这两轮评审都有阻断。双方各自坚持，以分歧结束，交给你裁决。
- **熔断二（`dissent`）**：评审不少于 2 位时，同一位评审连续 3 轮写「继续讨论」并带阻断，其他评审都没有意见，**而且每一轮都有人明确反对它的阻断**：其他评审对它上一轮的阻断写了【不同意】；其他评审写了【已解决】、它仍用原编号坚持（只在开了问题追踪时能认出）；或者主笔【不采纳】了它这一轮的阻断。没人反对（主笔都采纳、其他评审没有不同意、它每轮提的是新问题）不算分歧，讨论继续，直到收敛或到轮数上限。在主笔修订之后判断。
- **兜底**：轮数上限（`max`）。

**阻断原文存档**：每位评审一条，交给主席写主文档和判断追问，也存进讨论状态的 `blockers`。状态只看这位评审**最后一次发言的评审结论**；原文取最近一次写在**行首**、且那一轮结论不是「没有意见了」的【阻断】（和网页同一个判定），所以「本轮没有【阻断】」这类否定句不会再顶掉之前的真实阻断。分四种：仍在阻断（最后一次有行首阻断）；格式未识别（结论不是「没有意见了」，【阻断】却不在行首，照录最后一次的原文并附上更早写在行首的阻断，由主席判断）；没有意见了（之前的阻断照录，标明这次结论）；未再提（最后一次一个【阻断】都没写，标明从第几轮起）。后两种不算待裁决，照旧写 `clearedAt`。往前找时不越过最近一次「解决点」（这位评审写了「没有意见了」的那一轮，或者人的裁决；按裁决定稿的追问会记下 `ruledAfter`，即裁决覆盖到第几轮），所以已经解决的阻断不会再被翻出来当成未再提或未识别的附带。交给主席（写主文档、判断追问）和新会话追问的参与者时，另附一小节「已经解决的阻断」（最近 8 条，标明是评审写了没有意见还是人裁决过），不算待裁决，方便主席写「考虑过但没采用的做法」、判断评审有没有重提；待裁决卡片和讨论状态里的 `blockers` 不带这一节。熔断或到上限时另发一张「阻断存档 · 待裁决」卡片，只放前两种；正常收敛时不发。收敛和熔断的判定不变，仍然看任意位置的【阻断】。

**没收敛时的主文档**：熔断或到上限时，主席要把主文档写成能直接裁决的样子：要点里写结束原因、待裁决几条、最多 5 条分歧标题；「分歧与需要拍板的问题」逐条引用阻断原文，写双方理由和证据、主席的倾向和可选项；被核实结果否定、评审仍坚持的阻断单独列为「已核实不成立」，不算待裁决；「方案」写推荐方案并标「推荐方案（未经评审）」。你回一句追问「按某个做法定」或逐条裁决即可收尾。

## 限制

- 自定义机器人只能往群主时间线发消息，不能回复到话题，也不能接收 @。
- 单个机器人限频 5 次/秒、100 次/分钟；请求体上限 20 KB。程序会排队发送，超长内容截断，完整内容在本地网页上。
- 插话不是实时打断，要等到下一轮开始。
